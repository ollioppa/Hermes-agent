Why the separate reviews matter

Test the answer.
Then test the assumptions.

A capable agent can organise this method too. Decision Council provides the reusable instructions, review checkpoints and saved progress, so you do not have to coordinate them anew.

One agent gathers the evidence; you review it. Four more each examine a different question about that same evidence. They cannot see one another’s answers, so one early answer does not become the starting point for all four.

The outflanker is a further agent that challenges the assumptions shared by those reviews. The chair is the final reviewer: it weighs the arguments, explains the recommendation and identifies what could change it. Both receive the original evidence and all four findings.

That is seven separate agent calls. The outcome rests on the evidence, rather than a majority vote. Separate reviews can still share a mistake; they do not guarantee a correct answer.

A decision through the review

Would a small pilot actually solve the risk?

Fictional illustration. The documents, facts and responses below are invented to explain the method. This is not a recorded Decision Council run.

1. Agree what you are deciding

“Can we roll out the new service to every team on Monday?”

You supply the rollout plan and recovery notes. Decision Council helps frame the choice: proceed on Monday, use a limited pilot, or wait for missing checks.

You confirm the boundary—rollout readiness, including data recovery and support—and choose from the models the main agent proposes.

This is your first checkpoint: the question, boundary and models.

2. Review the evidence

  1. F1: The plan enables all teams on Monday morning. First use converts their stored records. Plan, §1
  2. F2: Switching back to the old interface was tested. Restoring converted records was not. Recovery notes, §2
  3. F3: Support training is scheduled for Monday afternoon, after launch. Plan, §3
  4. F4: A small pilot is possible, but it uses the same record conversion. Plan, §4

These are the example’s entire evidence base. In a real run, facts include source references, dates and uncertainty. You correct omissions before accepting them.

3. Four agents ask different questions

  • Which assumption is weakest?The plan treats a return to the old interface as recovery. Data restoration is still untested. F2
  • Which dependency could block the plan?Support is trained after the planned launch. Move that preparation before first use. F3
  • Where is the scope wider than it looks?This changes stored records, so readiness includes data recovery as well as enabling a service. F1–F2
  • Which step lacks a proven way back?The first record conversion. The supplied checks do not establish how to undo it. F1–F2

4. Challenge the tempting answer

“Start with a pilot” still needs scrutiny.

A smaller launch would affect fewer teams. But the outflanker challenges the assumption that reducing the audience makes the launch recoverable.

“The pilot converts records too. Fewer affected teams does not establish a way to restore their data.”

The decisive check is whether representative converted records can be restored and used by the old service. A smaller audience alone does not answer that question. F2, F4

5. Read the recommendation

Establish recovery before the first pilot.

The chair would not recommend the Monday rollout from this evidence. A pilot limits exposure, but its data recovery is still unproven.

Next check: rehearse conversion and restoration on representative disposable copies. Agree what counts as successful recovery, and prepare support before first use.

Revisit when: recovery and support readiness are demonstrated. Then assess a limited pilot against its agreed success and stop conditions.

Illustrative judgment based on F1–F4. No rollout or test is performed by this page.

What the extra challenge contributes

The independent reviews expose several weaknesses. The outflanker tests whether a seemingly sensible response—“make it smaller”—actually addresses the most consequential one.

The saved result gives you the recommendation, the reasoning and the evidence needed to revisit it. You remain responsible for what happens next; a Decision Council review does not approve or execute a change.

Give the review a basis

Point to what the answer depends on.

Use documents, logs, workspace files, IssueTracker tickets or CodeReview pull requests—the proposed code changes. A general question can also begin with your description alone.

For code questions, include the relevant code. A proposal or ticket description does not establish what the implementation actually does.

Use Decision Council to review <CodeReview PR link> against <IssueTracker ticket link>.
Use this workspace for context. Does the change meet the acceptance criteria?

Decision Council uses the access available in the execution environment. At fact review, check which sources were read, only partly read or unavailable, and whether code revisions match. Missing comments or inaccessible checks stay visible in the report.

Accepting the evidence does not make uncertain statements true. Ask for corrections before the four reviews; changed facts require a revised run that preserves the earlier record.

Your first checkpoint

Choose models for this question.

The main agent proposes concrete models available in your current environment and explains its recommendation. Choose a profile or adjust any role.

Every profile keeps the same seven agents and your fact review. One model can fill all roles in separate calls. Higher usage does not guarantee a better answer.

Profiles change the model allocation, not the review method.

Recognise the result

Read the reason.
Keep the next check.

The chat gives you a plain-language explanation and a link to the saved report.md. Use it to decide what to investigate or do next.

A complete review can be undecidable. That means the process finished, but the evidence cannot settle the question. An incomplete report means a required stage has not finished successfully.

What is recommended, and why?
Follow the argument from the original facts to the recommendation. Agreement among agents is not proof.
What remains uncertain?
Read the missing evidence and source gaps. A complete workflow does not make incomplete evidence sufficient.
What would change the answer?
Find the concrete next check and the condition for revisiting the decision.
What was outside the question?
Keep useful observations separate from the decision actually reviewed. The report also retains the findings, sources and model record.

You have a usable result when you can explain the recommendation, its evidence, its limits and the next check. Decision Council informs your decision; it does not approve or execute changes.

When you need it

Questions and help

Keep the saved report when something stops. It records completed work and the remaining issue.

The instructions are not loaded, or independent roles cannot run.

Ask the main agent to read SKILL.md and identify any missing file execution, independent-context or explicit-model-selection capability. Use only a verified supported execution route.

The host must support separate agent contexts and an actual way to select their models. Decision Council should explain the limitation before starting. The execution reference describes the checks.

A model or agent fails. Can I continue?

Ask the main agent to resume the saved run. Completed work is retained, and the failed role gets at most one retry. If its model is unavailable, choose a replacement when asked; other roles keep their models.

If the role still cannot finish, Decision Council returns the incomplete report and the concrete issue. A worker that validly reports “no finding” is different from a failed or missing worker.

I disagree with the recommendation.

Give a specific critique. You can request one revision by the chair using the existing facts and findings. The earlier report is preserved; this revision has one attempt.

New evidence or a changed question needs a new review. Do not treat a chair revision as a fresh analysis of information the earlier agents never saw.

Where are my files, and what does Decision Council remember?

Your chosen personal folder contains:

Your Decision Council folder/
  runs/<run-id>/report.md    Report and supporting run files
  council_kb.md              Confirmed improvements to the method

After a review, Decision Council may offer an optional reflection on how it worked. Its personal knowledge file keeps only method improvements you supply or confirm—for example, “Explain missing source access before asking me to accept the facts.”

Findings, verdicts, ticket content and project knowledge stay in the run files. Updating the skill preserves your personal files; they are separate from the distributed folder.

The remembered location is stored in ~/.config/council/location.json on macOS/Linux or %APPDATA%/council/location.json on Windows.

How do colleagues get Decision Council?

Keep the complete decision-council folder together and retain the MIT license and required notices. Each user checks capabilities as above and chooses their own report folder. See LICENSE for redistribution terms. Keep personal reports, source packets and model preferences outside the shared skill and Git repositories.

This guide works offline. Running Decision Council uses the model access provided by the execution environment. The local coordinator requires no additional model API key, Python packages or background service.

What has been verified, and what are the limits?

The coordinator has behavior tests using simulated agent responses. They check workflow and saved state. They do not prove that a cited claim is true or that a recommendation is correct.

A real run on the intended execution environment—including skill discovery, model selection and any IssueTracker or CodeReview access—still needs verification. The guide’s example is authored, not a recording.

A selected model name is also distinct from runtime identity actually exposed by the host. The report keeps those separate. Model reputation and confident wording cannot replace evidence.
