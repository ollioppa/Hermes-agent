# Sources and skill learning

## Sources establish the current case

Start with the actual project workspace, its instructions, canonical design and relevant code.
For a ticket or PR, use the connected tools available in that host. Record ticket/PR identifiers,
revision or commit, inspected files and the relevant requirements. Account for missing comments,
pages, diffs or checks as partial/unavailable. A description of a proposed change is not evidence
that the code implements it. An inaccessible source cannot be treated as empty or irrelevant.

Do not search unrelated folders for credentials or silently try a different account/site. Use the
configured authorized read access. Store source packets and analysis under the private run; the
coordinator performs no network access. Project files are edited only within the requested scope.

## Knowledge improves the method

The seed KB is shared reusable guidance. The personal registry improves how Delivery Workflow works for
its owner: diagnosis, scope selection, validation, evidence handling and explanations. Apply only
relevant entries, preserving their limits. A past project's finding is never evidence for a new one.

Suitable improvement: “Before marking integration complete, inspect which entry point actually
consumes the changed configuration.” Context: a configuration has several consumers. Limit: only
where more than one consumer exists.

Unsuitable entry: a ticket summary, a PR verdict, a customer fact, the content of a log, or the
solution to the current project's bug. Keep those in the run and canonical project documentation.

A completed report does not require learning or a separate reflection round. Only a
real user-supplied or confirmed method improvement can be saved. The schema restricts fields, but
the agent must still review whether the text is method guidance rather than disguised case content.

When a method rule no longer applies to the current design, retire or remove it with a reason from
the current task. Delete obsolete project validators, gates, guards and their active hooks as part
of the affected change. Keep relevant history in existing records without preserving dead controls
or adding a new governance layer. Prefer reuse and removal over additional tests or rules.
