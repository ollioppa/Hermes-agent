## Establish supported value without a sales pitch

Read the authoritative subject design and relevant evidence, including reasons for decisions and alternatives. Trace reader situation → limitation of the familiar approach → specific mechanism → useful outcome. A design states intent; an implementation shows what exists; an exercised check supports only what it observed. If they conflict, mark the gap before using the claim.

The fair alternative may be sufficient. Do not manufacture exclusivity or measured time savings. Remove the example temporarily: if the reason to use the subject disappears, the explanation is not yet grounded. A how-to needs a clear task and outcome instead of an adoption argument.

## Keep one short documentation baseline

Use the existing project design or clearly associated maintenance page. Record:

- reader, knowledge, primary starting state, goal and prerequisites;
- supported purpose/value, source references, alternatives and limits;
- required content and why it matters;
- reader paths and shared detail destinations;
- language, medium, actual review viewport and success criteria;
- binding decisions, their source, intended prominence, current location and open checks.

Before an edit read request, baseline and current document together. The current text alone does not prove all earlier decisions survived. For each affected decision record **preserved, rephrased, moved or deliberately replaced**, its new location and what was actually checked. Inspect unaffected content for accidental losses. Resolve conflicts before silently dropping requirements. This is an update to existing maintenance, not a new registry or per-message ceremony.

## Reader paths and visual checks

Quickstart supplies short answers and immediate action. Presentation explains purpose and relevant difference, develops the reasoning and fulfills the opening promise. A returning reader must not replay the explanation to act. Shortening Quickstart can move detailed setup behind a direct link; it cannot move its agreed brief purpose/value answer entirely into Presentation.

For introductory entries check benefit, graphic, next step and readable language together at the actual viewport. Ask whether the entry overloads the reader, explains the obvious or leaves direction unclear. Early feedback is for substantial unapproved redesign, not every small correction. The provisional browser viewport is 1366 × 768 at 100% zoom; include surrounding host UI. Mobile checking is a separate obligation when required. A Markdown source has no universal pixel layout.

A graphic explains a useful relation, uses readable labels and has a text equivalent. Do not rely on unsupported interactive elements or raw diagram syntax. A focused lookup can omit ornamental graphics and narrative. These boundaries retain the method's existing distinctions rather than applying every rule to every reply.

## Honest handover

Follow actionable instructions and inspect the intended destination where possible. Report actual checks and remaining ones. A valid link does not prove good explanation; a local browser does not prove wiki publication; an author-run task does not prove newcomer comprehension. Access and publication permissions are separate. No automatic quality score, extra reviewer fleet or new execution system is required.
