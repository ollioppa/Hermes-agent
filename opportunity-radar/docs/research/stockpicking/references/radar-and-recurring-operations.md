# Portable reference

Paths in backticks are relative to the package root unless explicitly described as output examples. Read only modules whose triggers apply. Provenance and excluded private inputs: `PROVENANCE.md` and `docs/research/conditional-inputs.md`.

### Mutating an admitted Opportunity Radar case

When the owner explicitly authorizes a live Radar status change after a deep dive, make the durable product state match the research verdict; do not stop at prose.

1. Identify and prove the product write path before promising the mutation: in `.`, list current cases with `PYTHONPATH=src python3 -m opportunity_radar.cli list --db state/opportunity_radar.sqlite3`, inspect the target symbol's current state and capacity, then read `--help` plus the owning CLI/DB method for the exact requested transition. Do not infer executable direct admission from the written product contract alone, and do not use unsupported ad-hoc flags such as `--status`; the CLI list command emits all cases. If the contract permits a transition that the live owner cannot perform, report the state as unchanged and seek explicit build authority for the smallest owner fix rather than routing through a semantically false intermediate state or writing SQLite directly.
2. For a newly admitted direct-READY case, build one complete payload before touching live state: full validated review, point-in-time HTTPS sources, `immediate_investable: true`, no `watch_condition`, and case/SPY/sector closes from the same executable market date with explicit currency, provider, retrieval time, and quote semantics. Put `Keine offene Bedingung; Review ist entscheidungsreif` or the equivalent economic statement in `missing_to_ready`; never encode the lack of a condition as a fake event. If the proposal is bound to a Candidate, use its explicit ID through the existing `promote-candidate` owner; admission and closing/linking that exact episode must be one transaction. Use `import-case` only for direct entry without a Candidate, not as a workaround that leaves a waiting Candidate open. Prove the chosen owner on a temporary SQLite database: `INBOX→READY`, zero watch conditions, one READY snapshot, a frozen shadow entry, neutral initial timing via `evaluate`, a READY reader render and, where applicable, the linked Candidate no longer awaiting admission. This is payload and product-path proof only, not evidence that live state changed.
3. After the isolated proof passes, import the unchanged payload exactly once into the live database. Read back through three independent boundaries: `list` for the durable status, `render` for the reader product, and `evaluate` for the bound shadow/READY dates. Also inspect the target case relationally and require exactly one `INBOX→READY` transition, zero watch conditions, one READY snapshot, the expected review/source count, and `immediate_investable = 1`. A successful import command without these live readbacks is not completion.
4. If the thesis changed for an existing case, append a new review version before the transition: create a minimal JSON payload with `review` and `sources`, then run `PYTHONPATH=src python3 -m opportunity_radar.cli revise-review --db state/opportunity_radar.sqlite3 --symbol SYMBOL --input /path/to/review.json`. Preserve the reason in review fields such as expectation, counterpath, falsifier, valuation, and `missing_to_ready` so the archive is explainable later.
5. Map the research verdict to the product state deliberately. Use `archive` for a consciously ended price episode or watchlist removal where the company may be revisited later; use `invalidate` only when the thesis/falsifier itself has broken. Record the user's authorization and the economic reason in the transition reason.
6. Render and verify the reader boundary immediately: `PYTHONPATH=src python3 -m opportunity_radar.cli render --db state/opportunity_radar.sqlite3 --output output/radar.md`; then re-list cases, inspect transitions/review versions, and mechanically check that the removed symbol no longer appears as `WATCH` while surviving symbols still do.
7. Run a narrow contract proof after mutation, for example `PYTHONPATH=src python3 -m pytest tests/test_cli_smoke.py tests/test_report.py tests/test_transitions.py`. Report the real test result and changed product status. Do not mix unrelated untracked research folders or other repo WIP into the status change.
8. If the company also appears in a domain radar such as BDC/private-credit, consult it for context but do not edit it merely because the Opportunity Radar case changed; mutate the canonical domain radar only when that system is the explicit target.

### Archived opportunities and history-preserving re-entry

1. Read the current product contract, archive transition, original Candidate episode and identity bindings before deciding whether a signal is genuinely new. Inspect all producer and admission paths; removing a scanner's symbol-exists filter alone leaves schema and manual admission inconsistent.
2. Keep an archived Case terminal. A confirmed later opportunity receives a fresh Case ID, review and shadow entry. Preserve old sources, snapshots, evaluations and position links. Limit symbol uniqueness to non-archived cases and retain historical identity aliases instead of overwriting the old binding.
3. Reuse the same DB-owned suppression predicate in screening and inside the existing admission transaction. Block non-archived duplicates, the same/earlier known episode and a signal month whose calendar month-end is not after the documented archive date. If required archive provenance is missing, do not invent it. Keep permanent EXCLUDE suppression separate. Reject a stale OPEN Candidate at admission as well, because it may predate an independently archived direct case. Explicit direct entry remains scanner-free.
4. Route symbol-based operations to the non-archived case, otherwise the newest historical case; apply that selection to position preview/import as well as the public lookup. Preserve already stored position Case IDs. Use `evaluate --case-id ID` for historical timing rather than allowing a new episode to reset the old shadow.
5. For SQLite history migrations, reuse the existing initialization owner. Verify a backup and rehearse on a real DB copy first. Disable foreign-key enforcement outside the migration transaction, copy/drop/rename only the affected owned tables while retaining original table names and record IDs, check foreign keys before commit, and restore enforcement after success or rollback. Compare every pre-existing table row, not only counts, and run initialization twice to prove idempotence. Remove obsolete per-initialization identity seeding rather than guessing new links on every read.
6. Before live schema work, pause the actual consumers and check for in-flight writers. After migration, read back historical links, current reader and quarterly context; resume the same jobs with unchanged bindings and schedules. Use isolated synthetic admissions to prove re-entry, never live investment records merely as a demonstration.

### Autonomous recurring operation

1. Bind the deterministic screening output to a durable candidate identity and signal episode before research begins. Carry the selected row ID and unchanged `first_entry_month` through `candidate-decision --candidate-id ID --signal-date FIRST_ENTRY_MONTH`; symbol alone cannot distinguish listings or later episodes. Make an identical retry return the existing decision ID even after episode deferral, without reopening it or applying the old result to a later OPEN row. Once an `OPEN` candidate has a pending decision or revisit boundary, never overwrite its bound episode when a later scan sees the same identity: update observation metadata only, or create a later episode after the old one is resolved. Otherwise a selector that compares `decision.signal_date` with mutable candidate metrics silently makes `AWAITING_USER` or not-yet-due research eligible again.
2. Let a bounded worker claim exactly one unreviewed candidate, run the lean first pass, and deepen only a surviving case. Limit acquisition to the few current primary sources needed for the dispute and reserve time for synthesis; unfinished research that never crosses into reader prose is not a result.
3. Persist both the disposition and its reason. Translate the completed analysis result after every phase, not just the first pass: economic DROP becomes episode deferral, one genuine decisive evidence blocker gets an explicit revisit, and a complete positive proposal awaits the owner. Require a nonempty existing report and reader summary before recording decision-ready research; neither file presence nor an old status label proves substantive analytical completeness. Distinguish:
   - permanent identity exclusion, which only the owner may authorize;
   - episode deferral, which suppresses the same signal episode but permits a genuinely new episode;
   - decision-ready research, which leaves the candidate open for the owner.
   Enforce human-only exclusion in the durable writer by actor/authority, not only in the prompt; an autonomous caller must fail without changing candidate state.
4. Make screening consult that persisted decision before filling candidate capacity. Archiving a candidate without consulting its prior decision merely causes it to be selected again on the next cycle. Normalize blank revisit triggers to `NULL` and accept only canonical `YYYY-MM-DD` revisit dates before any SQLite lexical comparison; Python ISO parsers may also accept compact or week-date forms whose strings sort incorrectly.
5. Automatically defer clear machine-reviewed rejects only for their current episode. Keep routine research silent and surface completed candidates through the appropriate reader product: watch-worthy and current decision candidates belong in the quarterly WATCH letter unless the owner explicitly requests an event-driven alert. Silence is valid when nothing survives.
6. Never convert an automated research verdict into `WATCH`, `READY`, or a permanent exclusion. Those are final human decisions.
7. Prove the recurrence boundary in an isolated state: archived candidates do not reappear in the same episode, permanent exclusions remain suppressed, a new episode can reopen a deferral, and decision-ready research stays open without promotion.
8. For recurring mail delivery, verify the whole delivery boundary, not just the report renderer: Markdown→HTML conversion, SMTP submission, exact Sent-folder header match, and a durable receipt that makes a second run idempotent. Pin helper interpreters by absolute path in cron-owned mailers; reduced cron environments can drop user-site packages and turn a working interactive `python3` into a failing scheduled renderer.

### Quarterly WATCH review and reader delivery

Use a separate quarterly product for opportunities that are interesting but not owned:

1. Keep actual holdings in the monthly portfolio letter and opportunities in the existing quarterly product. Include already admitted READY cases as a separate quarterly group rather than letting them disappear between WATCH and purchase; distinguish them from not-yet-admitted decision-ready Candidates. Exclude a READY case from that group only through an explicitly linked ACTIVE position. A missing link does not prove nonownership, and a matching ticker does not authorize a guessed link. Never merge raw scanner queues, dropped/deferred cases, archives or operational logs into either product.
2. Start from stored thesis, condition and falsifier; perform a bounded evidence delta, not a full rerun. Also bind current compatible price, original endpoint, remaining duration and remaining opportunity against SPY in EUR. Thesis intact is not proof of current attractiveness. A material loss of asymmetry requires human recheck, never automatic status or order.
For an admitted READY case, start from its stored thesis, falsifier and valuation assumptions; review only material new evidence. Distinguish continued support, a required recheck, a broken thesis and insufficient evidence as letter recommendations, never automatic Radar transitions. A historical entry/reference price alone cannot establish current investment readiness.
3. Include a completed unowned candidate only when its stored decision is bound to the current signal episode. Use `WATCH_PROPOSAL` only when the economic case remains positive and exactly one observable condition is still missing. Show `DECISION_READY` separately rather than inventing a WATCH condition. Keep `NOT_WATCH`, unfinished research, raw scanner hits, and deferred/archive inventories out of the reader-facing letter.
4. Write for the reader in this order: plain-language orientation, existing WATCH cases, already admitted READY cases, new WATCH proposals, not-yet-admitted decision-ready proposals, explicit decisions needed from the owner, then sources. Explain what the letter is, why each item matters, and what it means in practice before exposing internal labels.
5. Bind the actual final body bytes to the context used: reviews, conditions, position episodes/baselines, holding links and read report bytes, not just paths or symbol list. Mailer reads and sends the same verified body once. A changed body is not an already delivered new version; ambiguous attempts fail closed. This is content binding plus Sent-header verification, not MIME-equivalence proof.
6. Send one verified email per quarter only after the manifest is complete. Persist an attempt marker before SMTP; if the send outcome is ambiguous, recover the exact message from Sent or fail closed rather than resending. Prove the new delivery path live before retiring older periodic mails, and preserve their history when disabling them.
7. Keep any event watchdog deterministic and silent. It should wake the reader only when a defined WATCH condition actually changes; the quarterly letter is the normal review surface.

### Bound market observation and reader consistency

1. Read the original bound snapshots before refreshing a case. Preserve the distinction between the internal Case symbol and the provider's actual listing identifier; bind response identity, currency, instrument type and price basis. Normalize only demonstrated legacy provider labels. Never infer a foreign listing from a bare ticker, silently switch providers, or compare adjusted and unadjusted prices.
2. Select a shared trade date from actual available completed bars for Case, benchmark and sector. Do not forward-fill, relabel an intraday price as a close, or move a price to a convenient date. Fetch and validate the full set before storing it in one transaction; a source failure is an operational limitation, not an economic rejection.
3. Reuse series binding and price-return arithmetic at the existing market owner; current/latest selection differs from historically bound READY/outcome endpoints. Keep incompatible history unchanged and unresolvable old endpoint sets explicitly unknown. Suitable newer outcomes reach reader/watchdog; dates, not insertion order alone, determine recency. Preserve confirmed local-price alarm semantics.
4. Report local-price comparisons as such. Different assets may retain different explicitly bound quote currencies; that is not an FX-normalized investor return or Total Return. Prove the real fetch on a database copy first, then perform only an authorized normal refresh and exact reader readback, identifying which observational rows changed and which investment states stayed unchanged.

### Candidate-research failure classification

Do not let a bounded worker turn its own acquisition limit into an investment verdict.

1. Apply the tight source budget to the comparative first pass. If the motor survives, permit the bounded additional primary documents needed to finish the historical spine, shareholder bridge, financing and valuation; a single hard cap across both stages systematically manufactures incomplete negative cases.
2. Distinguish four outcomes explicitly:
   - economic rejection for the current signal episode;
   - decision-ready research awaiting the owner;
   - one decision-relevant evidence blocker with a dated or event-bound revisit;
   - a distorted screen whose corporate action, rights issue, acquisition, split or shock baseline makes the price signal uninterpretable.
3. Archive a distorted signal episode without describing it as evidence that the company is poor. Keep an incomplete case from being selected again immediately; persistence must carry its revisit boundary.
4. Do not use a missing quote, share count, enterprise value or other normally recoverable metadata as the reason for economic rejection. Acquire it during the surviving deep dive or record a bounded research blocker.
5. Shadow a revised runtime prompt against representative old cases before cutover. Compare disposition, carrying claims, counterevidence, valuation boundary and falsifier; if the model changes at the same time, label the comparison as prompt-plus-model rather than attributing the result to wording alone.

## Lifecycle extension map and scope firewall

Before extending screening or Radar into purchased-position monitoring, create one short plain-language map that a non-developer can use without translating workflow jargon:

1. Describe the productive path as it exists now, then the proposed path; label drafts and missing runtime explicitly.
2. For every stage state the decision it supports, why it exists, who may change its state, and what it must never change.
3. Mark mature components as frozen islands by exact authority. Change only their interfaces unless the owner explicitly reopens their contents.
4. Trace the surrounding runtime far enough to find direct dependencies, but do not turn adjacent defects into project scope. Include a mismatch only when it blocks one of the named user outcomes; otherwise park it visibly.
5. Require every implementation package to point directly to an original user outcome. If it cannot, remove it from the build even when an integration review found a real defect.
6. Review the bounded map against the live schema, CLI, scheduled prompt, representative outputs and tests. Use one independent review to find material contradictions; do not create a review-of-review loop unless a concrete finding remains unresolved.
7. Turn each in-scope mismatch into the smallest correction at its real owner. Prefer one existing command, transaction, readback and focused behavior test over new gates, queues, receipts or validators.

Write the reader map as `today → target → build order → explicit non-goals`, and keep it materially shorter than the implementation plan. Use everyday German and explain what and why before file names, schemas, model names, or implementation mechanics.
